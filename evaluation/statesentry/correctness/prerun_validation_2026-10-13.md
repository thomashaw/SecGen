# Pre-run validation, 13 October 2026

This file records the checks made before the detection-correctness run, so that the
conditions of the reported run, and the defects the checks exposed, can be cited in
the revised paper (DESSERT 2026, paper 121). It comprises a static analysis of the
detection code on this branch and a read-only inspection of the experiment VMs. The
correctness test itself had not been run when these checks were made.

The VM observations were collected over the QEMU Guest Agent (as root) and are
transcribed from the inspecting agent's report rather than captured as raw logs; the
static predictions can be reproduced with `combined_path_sim.rb` in this directory.

`/etc/auditbeat/audit.rules.d/auditbeat_rules_file.conf`, contains:

## How `combined_path` is computed

`modules/services/unix/logging/logstash/files/combined_path.rb:26-32` always joins
`process.working_directory + "/" + file.path`, even when `file.path` is already
absolute, and then applies two string operations. `remove_duplicates` keeps only the
text between the first and second `//` (and discards the rest), and `remove_relative`
removes `..` segments lexically, leaving `.` in place and never resolving symbolic
links. Absolute paths therefore normalise correctly only because the join produces
exactly one `//` when the working directory is not `/`. The output of
`ruby combined_path_sim.rb ../../../modules/services/unix/logging/logstash/files/combined_path.rb`
follows ("MATCH" means the path alone would satisfy the rule; the reader, result and
user conditions are applied separately in the table after it).

## Findings for the paper

1. **No user attribution.** Neither the filter nor the ElastAlert rule checks which
   account read the file, so a read of `/etc/shadow` by root (or by any account able to
   read it with an accepted reader) registers progress for the goal (N05).
2. **Reader paths are compared literally.** The rule matches the full executable path,
   so `less` is never accepted on this base because it resolves to `/bin/less`; this is
   a false negative for a reader the design intends to accept, in addition to the
   expected exposure for readers outside the list.
3. **Path normalisation is lexical and fragile.** `combined_path` does not remove `.`,
   discards everything outside the first `//` pair, and does not resolve symbolic links.
   Consequently a process whose working directory is `/` is never detected for an
   absolute path (`//etc/shadow`), reads through a symbolic link are missed (P07), and
   decoy paths containing `//` or a symbolic link followed by `..` can produce false
   detections (X1 to X3).
4. **Audit scope follows the top-level directory.** Watches are placed on `/etc/` and
   `/home/` (the first component of each goal path), so all reads beneath them are
   collected; the scope of collection therefore depends on which goals a scenario
   defines rather than on the goal file alone.
